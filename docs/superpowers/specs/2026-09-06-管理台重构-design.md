# 管理台重构设计（路由化信息架构 + 员工管理后台化 + 消息中心与通知渠道）

日期：2026-09-06 ｜ 状态：已与用户对齐，待评审

## 背景与需求

现有管理台（apps/console）是横排 tab 单页切换（无路由，刷新丢状态），员工直播是纯滚动事件
时间线，员工档案来自 yaml 配置只读，提醒信号埋在页面里不主动。用户要求重构为：

**首页面板 → 任务中心 → 数字员工管理（下钻：员工→任务→执行详情→直播）→ 消息中心 + 外部通知渠道。**

与用户确认的决策：

| 决策点 | 结论 |
|---|---|
| "后台可配置"范围 | 数字员工档案（增删改、盯梢等级、能力绑定）；班组关系本版不动（用户确认暂时不要班组） |
| 直播节点划分 | plan 任务按任务节点分组；老任务（无 plan）回退滚动时间线；新事件自动滚动到底 |
| 导航 | 引入 vue-router（URL 可直达/刷新不丢）+ 左侧边栏布局 |
| 员工×能力 | **每员工绑定能力 kind**（空=全部可用，向后兼容）；分派时校验任务项 kind ∈ 员工绑定 |
| 消息提醒 | 三类：待放行/任务失败/任务完成；服务端存储已读状态；右上角消息模块统一查看，点击直达详情 |
| 外部通知 | 保留对接钉钉机器人/企业微信机器人/通用 Webhook，后台可配、多渠道并存 |
| 任务创建 | 三模式：表单/yaml（现状保留）+ **AI 解析生成**（大模型解析自然语言→用户确认后添加） |
| 任务生命周期 | 增加 **draft 发布态**：创建后默认草稿，显式发布后才可被数字员工接取/分派 |

## 方案取舍

| 方案 | 说明 | 结论 |
|---|---|---|
| vue-router + 侧边栏 | 深层下钻（员工→任务→直播）URL 化，刷新/分享/前进后退可用 | **采用** |
| 保持 tab 切换只重排菜单 | 零新依赖但刷新丢状态、深链做不了 | 否——层级变深后体验更差 |
| 消息服务端存储 | MessageStore 落 dataDir，已读多端一致、有完整历史 | **采用**（用户明确要服务端） |
| 已读存浏览器 localStorage | 简单但换浏览器/刷新不一致 | 否 |
| WebSocket 推送 | 实时 | 否——现有轮询模式（2s/5s）量级足够，内网场景 YAGNI |
| 员工删除 | **删除=停用**（enabled=false），不物理删——历史任务 claimedBy 引用不断 | 采用 |
| 直播"发送指示" | 接上（现有 steer 事件悬空未接）——盯梢场景有用 | 采用 |

## 设计

### 1. 信息架构与路由（vue-router）

**布局**：`el-container` 左侧边栏（`el-menu` vertical）+ 顶栏（标题 + 右上角消息铃铛），
内容区 `<router-view>`。

**路由表**：

| 路径 | 页面 | 说明 |
|---|---|---|
| `/` | Dashboard.vue | 首页面板 |
| `/tasks` | TaskCenter.vue | 任务中心（列表+筛选+新增发布） |
| `/tasks/:id` | TaskDetail.vue | 任务详情（现有组件增强） |
| `/employees` | Employees.vue | 数字员工管理 |
| `/employees/:id` | EmployeeDetail.vue | 员工详情（档案+当前任务+历史任务） |
| `/employees/:id/live` | EmployeeLive.vue | 员工直播（重构） |
| `/reviews` | CheckReview.vue | 人工放行（功能不变） |
| `/audit` | AuditLog.vue | 审计台账（功能不变） |
| `/capabilities` | Capabilities.vue | 能力管理（功能不变） |
| `/channels` | Channels.vue | 通知渠道配置（新增） |

- 侧边栏菜单项：首页面板/任务中心/数字员工/人工放行/审计台账/能力管理/通知渠道；
- 菜单徽标：「人工放行」挂待审数、「任务中心」挂失败数（红色数字）；
- 现有 TaskPool.vue 的列表职责并入 TaskCenter.vue（新建对话框 TaskCreateDialog.vue 保留复用），
  TaskDag.vue 编排视图保留（任务中心内切换"列表/编排"）。

### 2. 首页面板（Dashboard）

- **员工卡片**：每员工一卡——姓名/角色、忙闲状态（roster busy）、能力徽标（绑定的 kind，
  空=「全部能力」）、完成任务数；点击直达 `/employees/:id`；
- **任务统计卡**：进行中（claimed+running）/已完成（done）/失败（failed）/待放行（checks 待审数）
  四个数字卡；失败卡红色，点击跳 `/tasks`（带状态筛选）；
- 数据来源：现有 `GET /api/employees` + `GET /api/tasks` + `GET /api/checks` 前端聚合
  （量级小，不加聚合接口，YAGNI）；5s 轮询。

### 2.1 任务创建三模式与发布状态（用户追加需求）

**任务创建三模式**（TaskCenter 的新增入口，前两种为现状保留）：

1. **可视化表单**（现有 TaskCreateDialog 表单模式，零改动）；
2. **yaml 直贴**（现有，零改动）；
3. **智能生成（新增）**：文本框粘贴自然语言需求描述 → 点「AI 生成」→ 后端大模型解析为
   任务包草稿 yaml → 前端以 yaml 模式预填展示 → 用户检查/修改 → 确认添加。流程：
   - 后端 API：`POST /api/tasks/parse`（body `{description: string}` → 返回 `{yaml: string}`，**不落库**）；
   - 实现：console-api 调用已装配的 ModelGateway（chat 路由）——系统提示词含任务包 schema
     说明 + **当前能力注册表已启用的 kind 列表**（生成的 kind 必须取自注册表）+ yaml 输出约束；
     用户描述作为 user 消息；取回复中的 yaml 代码块；
   - 服务端解析校验：回复经 `parseTaskPackage` 验证，不合法 → 400 可读（前端提示改用表单/yaml 模式）；
   - 未配置模型网关 → 400「未启用智能生成（未配置模型）」；
   - **用户确认后才创建**——生成结果只是预填，不直接入库。

**任务发布状态**（生命周期：draft → pending → …，只有发布后可被接取/分派）：

- `TaskStatus` 增加 `'draft'`；`POST /api/tasks` 创建后默认 **draft**（有意的行为变化：
  不再创建即可被接）；
- 新 API：`POST /api/tasks/:id/publish`（仅 draft 可发布 → pending；否则 409 可读）；
- 调度器无需改造——现状只分派 pending，draft 天然隔离；
- 前端：任务中心列表 draft 徽标（灰「草稿」）+ 行内「发布」按钮；TaskCreateDialog 确认
  文案改「保存为草稿」；Dashboard「进行中」统计不含 draft；
- 现有脚本/e2e（demo.mjs、rehearsal 等）创建任务处补 publish 调用（实施时同步改）。

### 3. 数字员工管理（档案后台化）

**数据模型**（`EmployeeRecord`，console-api）：

```ts
interface EmployeeRecord {
  id: string;            // 唯一键：'emp-01'
  name: string;
  role: string;          // 主岗位（展示）
  skills: string[];      // 可接任务岗位集合（现有 EmployeeProfile.skills 语义不变）
  /** 能力 kind 绑定（本次新增）：任务项 kind ∈ 此集合才可执行该项；空/缺省 = 全部可用 */
  capabilities: string[];  // kind 引用能力注册表；保存时校验 kind 已注册
  /** 员工专属模型绑定（可选，2026-09-06 增补）：一人一模型一 key；缺省回退全局 routes */
  model?: EmployeeModelBinding;
  supervision?: SupervisionPolicy;  // 盯梢等级，缺省 shadow
  enabled: boolean;      // false = 停用（调度不再分派；不物理删）
  createdAt: number;
}
```

**存储**：`FileEmployeeStore`（`<dataDir>/employees.json`，mutate 队列串行化，与
FileCapabilityStore 同模式；员工个位数，file 足够）。

**seed 迁移**：首次启动文件不存在时，把现有 runtime yaml `employees:` 段（`opts.runtime.profiles`）
导入为初始档案（capabilities 置空=全部可用、enabled=true）；之后**以后台为准**——
yaml 再改不生效（文档写明）。

**API**：

| Method Path | 说明 |
|---|---|
| `GET /api/employees` | 列表（含 busy/runningTasks 现有字段 + enabled/capabilities） |
| `POST /api/employees` | 新增（id 冲突 409；capabilities 校验 kind 已注册） |
| `PUT /api/employees/:id` | 修改（同校验） |
| `DELETE /api/employees/:id` | 停用（enabled=false，可读提示"已停用而非删除"） |

**模型绑定（2026-09-06 增补：一人一模型一 key）**：

- `EmployeeModelBinding`：`{ baseUrl: string; apiKey: string; model: string; api?: 'openai-completions' | 'anthropic-messages' }`（与 runtime ModelSpec 同构，api 缺省 openai-completions）；
- 绑定了 model 的员工，执行其任务时用**专属 gateway**（按该员工 model 构造单路由 ModelGateway，
  覆盖 chat 路由）；未绑定回退全局 routes（现有 yaml 员工/行为零变化）；
- 注入点：inproc = `createEmployeeExecutor` 内按员工覆盖（`EmployeeExecutorOptions` 增
  `modelFor?: (employeeId) => ModelSpec | undefined`，server 装配从 EmployeeStore 取，
  取值时经 resolveSecret 支持 `enc:v1:` 密文）；fork = job 下发带 `employeeRoute`
  （worker 构造 gateway 时追加在 routes 尾部，Map 构造语义后者覆盖同 callType）；
- apiKey 安全：`GET /api/employees` **脱敏**返回（apiKey → `'***'`）；PUT 时 apiKey
  留空或 `'***'` = 保持原 key 不变（新增绑定 apiKey 必填）；
- **能力注册表与模型彻底解耦**（kind 只管工具集，不做模型区分）；任务 AI 解析
  （POST /api/tasks/parse）走全局模型不变；
- 模型连通性测试按钮不做（YAGNI：配置错误在执行失败事件留痕可见，下版可加）。

**执行链接线**：
- `EmployeeRoster` 现为一次性内存构造（yaml profiles）。改为：**EmployeeStore 为唯一事实源**，
  调度装配处从 store 读启用的员工构造 roster；每次调度 tick 前用 store 当前内容刷新
  （后台改动下个 tick 生效，无需重启）；
- 分派校验扩展（plan 任务）：任务项 kind 执行前校验 `员工 capabilities 为空 ∨ 包含该 kind`，
  不满足 → 该员工不接此单（readiness 判定跳过），任务留池等其他员工；全部员工都不满足
  → 任务保持 pending，事件留痕「无员工具备能力 X」。

### 4. 员工详情与下钻链路

`/employees/:id`：
- 上半区：档案卡片（name/role/skills/supervision/capabilities/enabled）+「编辑」按钮（对话框同新增）；
- 下半区两个 tab：
  - **当前任务**：`GET /api/tasks?claimedBy=:id&status=claimed,running`；
  - **历史任务**：`GET /api/tasks?claimedBy=:id&status=done,failed`（含结果摘要与时间）；
- 任务行点击 → `/tasks/:id`；执行中任务行有「进入直播」→ `/employees/:id/live`；
- 后端：`GET /api/tasks` 增加查询参数 `claimedBy`、`status`（逗号分隔多值），不传行为不变。

### 5. 员工直播重构（EmployeeLive.vue）

- **plan 任务**：按任务节点分组——每个 plan 项一个节点块：
  - 块头：`第 N 项 · <title>` + 状态徽标（进行中=高亮蓝 / 已完成=绿 / 失败=红 / 待执行=灰），
    数据源 = 任务 planProgress + 当前执行位置（最新 plan 事件）；
  - 块体：该节点的事件时间线（tool_call/task_check/verify 结果），按 plan 事件的
    `payload.plan.itemId` 归组（plan-runner 每项 start/done/failed 事件已带 itemId）；
  - **当前节点块自动展开并滚动到可见**（2026-09-06 澄清：「置顶」指视觉滚到可见，不做 DOM 重排——保持计划项 natural order 使「第 N 项」序号成立），其余可折叠；
- **老任务（无 plan）**：回退现有滚动时间线（不分组）；
- **自动滚动**：新事件到达时若用户已在底部附近（容差 40px），自动滚到底；用户上翻浏览时不打扰；
- **发送指示**：接通现有悬空的 steer 事件——输入框 + 发送，走现有 steer API（下达指示给执行中员工）；
- 轮询维持 2s + since 增量。

### 6. 消息中心（服务端）

**数据模型**（console-api `MessageStore`）：

```ts
interface MessageRecord {
  id: string;
  type: 'review_required' | 'task_failed' | 'task_done';
  title: string;         // '任务 feat-login 待放行'
  summary: string;       // 摘要（员工申报/失败原因/完成情况）
  taskId: string;
  employeeId?: string;
  createdAt: number;
  readAt?: number;       // 服务端已读
}
```

- **存储**：`FileMessageStore`（`<dataDir>/messages.json`，只保留最近 1000 条，超出丢弃最旧）；
- **生成**：EventBus 上挂消息 sink——监听三类事件自动生成：
  ① task_check 事件 `awaiting=true`（待放行）② 任务 outcome failed ③ 任务 outcome done；
  消息生成与渠道推送同点触发（见 §7）；
- **API**：
  - `GET /api/messages?unreadOnly=1` → `{ messages, unread }`；
  - `POST /api/messages/:id/read`；
  - `POST /api/messages/read-all`；
- **前端**：顶栏铃铛 + 未读红点数字；点开抽屉（el-drawer）列消息（类型徽标/标题/时间/已读态），
  **点击 → 对应详情**（review_required→任务详情、failed/done→任务详情），单条已读、
  「全部已读」按钮；新消息到达时 el-notification 右上角弹窗（失败类红色），点击同样直达；
  5s 轮询未读数。

### 7. 外部通知渠道（后台可配）

**数据模型**（`NotificationChannelDef`）：

```ts
interface NotificationChannelDef {
  id: string;
  type: 'dingtalk' | 'wecom' | 'webhook';  // 钉钉机器人/企业微信机器人/通用 Webhook
  name: string;          // 展示名
  webhookUrl: string;
  secret?: string;       // 钉钉加签（可选）
  enabled: boolean;
}
```

- **存储**：`FileChannelStore`（`<dataDir>/notification-channels.json`，同 store 模式）；
- **API**：`GET/POST /api/notification-channels`、`PUT/DELETE /api/notification-channels/:id`、
  `POST /api/notification-channels/:id/test`（发送测试消息，回传成功/失败原因）；
- **推送**：消息生成时（§6 三类）同步 POST 到所有启用渠道：
  - dingtalk：`{"msgtype":"text","text":{"content":"..."}}`（含加签计算）；
  - wecom：`{"msgtype":"markdown","markdown":{"content":"..."}}`；
  - webhook：原样 JSON `{type,title,summary,taskId,consoleUrl}`；
  - 内容含任务名 + 摘要 + 控制台直达链接（`consoleUrl` 从配置取，缺省空）；
  - **失败只记事件日志，不阻断、不重试**（渠道可用性靠测试按钮验证）；
- **前端**：`/channels` 页——列表（类型徽标/名称/URL 脱敏展示/启停开关）+ 新增/编辑对话框
  + 每行「发送测试消息」按钮。

### 8. 错误处理

| 场景 | 处理 |
|---|---|
| 新增/修改员工 id 重复 | 409 可读 |
| capabilities 引用未注册 kind | 400 可读（保存时拦） |
| 任务项 kind 不在任何在岗员工绑定内 | 任务保持 pending，事件留痕「无员工具备能力 X」 |
| 停用员工有执行中任务 | 允许停用；执行中任务照常跑完，之后不再分派 |
| 消息/渠道文件损坏 | 读错误区分 ENOENT，损坏不静默降级为空（同 capabilities 修复模式） |
| 通知渠道推送失败 | 记事件日志，不影响消息中心与主流程 |

### 9. 兼容与迁移

- 现有页面（能力/审计/放行）功能零删减，只换布局挂载；
- 老 yaml `employees:` 段仅在 employees.json 不存在时作 seed，之后以管理台为准；
- `GET /api/tasks` 新参数不传时行为不变（零回归）；
- **创建即 draft 是有意的行为变化**（用户要求发布才可接）：现有脚本/e2e 补 publish 调用；
 除此之外 `POST /api/tasks` 请求格式与校验零变化；
- EmployeeProfile 类型不动（capabilities 绑定在 console-api EmployeeRecord 层，
  分派过滤在装配层做，runtime 不感知）；
- 员工模型绑定同样不进 runtime 类型（EmployeeRecord.model，执行注入走
  modelFor/employeeRoute 装配项）；未绑定模型 = 全局 routes，零回归。

## 不做的事（YAGNI）

- 不做班组关系后台化（用户确认暂时不要）；
- 不做 WebSocket/SSE 实时推送（轮询够用）；
- 不做消息的按类型订阅/用户体系（单管理员场景，已读全局共享）；
- 不做通知渠道的重试/退避（失败留痕 + 测试按钮足够）；
- 不做钉钉/微信 OAuth 回调（只发不收）；
- 不做 Dashboard 自定义卡片布局（固定布局）。
