# 任务计划与能力注册表设计（单员工任务链 + 后台可配能力）

日期：2026-09-05 ｜ 状态：已与用户对齐，待评审

## 背景与需求

数字员工的任务执行需要"计划式"模式：**在一个任务包里预先规划任务1/任务2/任务3，
数字员工按计划逐项执行**（例：开发 → e2e 测试 → 提交 git → 发布）。

与用户确认的决策：

| 决策点 | 结论 |
|---|---|
| 模式取舍 | 单员工任务链为主（本设计）；跨工种流转用"拆多个任务包 + dependsOn"实现（现有机制，天然隔离） |
| 失败处理 | 失败即停、可续跑（人工处置后从失败项恢复，前面已完成项不重做） |
| 工具链绑定 | **声明式**：任务项声明 kind，系统按 kind 映射工具集（权限边界）；**调用时机**由模型在授权工具集内自主判断 |
| 扩展性 | kind 必须可扩展：**能力注册表 + 后台配置管理**，新能力手动配置接入，不写死枚举 |
| 首批范围 | 注册表机制 + dev/test/commit/devops 四类全做（devops 接入 mcp-deploy，目标环境先指演示环境） |

## 方案取舍

| 方案 | 说明 | 结论 |
|---|---|---|
| A. 计划执行器 | tasks 升级结构化计划，executor 内逐项驱动同一员工同一会话，进度落库、失败即停、可续跑 | **采用**——任务项上下文天然传递，停点/续跑是系统能力 |
| B. 链展开成多任务记录 | 一个任务包自动拆 N 条 TaskRecord 串 dependsOn | 否——违背单员工语义，每项换实例丢上下文 |
| C. 纯提示级顺序 | 只在简报里编号+顺序要求，无系统状态 | 否——失败即停/续跑做不到 |
| 工具链由模型判断 | 不做 kind 绑定，全量工具可见 | 否——银行内网权限必须声明式、可审计；模型只在授权范围内决定"何时调" |

## 设计

### 1. 任务包格式（TaskPackage.tasks 升级）

```yaml
taskId: feat-login
title: 登录功能开发
repo: { url: "http://localhost:3000/demo/web-app.git", branch: develop }
plan:
  - id: t1
    kind: dev
    title: 开发登录接口与页面
    detail: 实现 POST /api/login，前端登录表单，含单元测试
  - id: t2
    kind: test
    title: e2e 测试登录流程
    detail: 覆盖正确/错误密码、锁定策略
    verify: npm run e2e        # 可选：执行器亲自跑，退出码判定该项过不过
  - id: t3
    kind: commit
    title: 提交代码并建 MR
    detail: 提交到 feature 分支并建 MR 至 develop
  - id: t4
    kind: devops
    title: 发布到测试环境
    detail: 部署 test 环境并确认部署完成
role: backend
```

- 每项：`id`（包内唯一）、`kind`（**可选，缺省 `dev`**：能力类型，查注册表）、`title`、
  `detail`（该项要做什么）。缺省落到基础工具集（bash+文件读写）是最小权限——
  放大权限的项（commit/devops）必须显式声明 kind，审计时可追溯；
- **与老字段 `tasks` 的关系**（现状修正：`tasks` 是 `DevTask[]` 结构化清单，非字符串列表）：
  老 `tasks: DevTask[]` 语义**原样保留**——无 `plan` 字段的任务包走现有单次执行路径
  （简报 + task_check 节点申报），零回归；`plan` 与 `tasks` **互斥**，同时存在解析报错可读；
  有 `plan` 时 `tasks` 可省略，计划模式下 task_check 的申报粒度 = plan 项 id；
- `dependsOn` / `supervision` / 报告通道等字段零改动。

### 2. 计划执行器（Plan Runner）

**位置**：executor 内新组件；调度器只认任务包整体，链内推进是执行器的事。

**执行模型**：一个员工实例、一个会话从头跑到尾（任务 2 直接看得到任务 1 写的代码）。逐项循环：

```
对每个任务项（按声明顺序）：
  1. 查能力注册表：kind → 本项可用工具集
  2. 以"第 N/M 项：<title>"为指令 + 注入本项工具集，驱动员工执行
  3. 员工 task_check 申报（带证据：做了什么 + 验证命令输出摘要）
  4. 若该项配了 verify 命令 → 执行器亲自跑一遍，退出码 0 才算过
  5. 通过 → 该项 done，进度落库；失败 → 链停：任务整体 failed + failedItemId，后续项不动
```

**任务项状态判定（三层控制，客观信号优先，不信模型自评）**：

1. **员工申报**：task_check 按项申报，必须附证据（操作摘要 + 验证输出），只是起点；
2. **verify 命令**（任务项可选字段）：员工申报后**执行器亲自运行**（如 `verify: npm run e2e`），
   退出码 0 该项才 done——与模型无关，模型骗不过；dev/commit 项同样可配（如 `npm run build`）；
3. **supervision 闸门**：shadow 级申报后等人工放行（现有节点验收）才推进；trusted 级
   申报（+verify）通过即自动推进，事后台账审计。三层叠加，任何一层不过即失败停链。

**放权后的保障（人工 check 关闭时）**：人工闸门只是 shadow 过渡层，最终放权（trusted）
后两道永久护栏不变——①**工具权限边界**：每项可用工具由能力注册表按 kind 锁死，
与盯梢等级无关，模型用不到自己没有的工具；②**verify 客观校验**：人工撤出后任务项
过不过的最后一道客观关卡。因此 commit/devops 等放大权限的关键项**建议必配 verify**；
配合失败即停 + 全程事件台账，零人工参与下依然闭环可审计。

**状态机**：任务顶层状态不变（pending→claimed→running→done|failed），TaskRecord 扩展：

```ts
planProgress: { itemId: string; kind: string; title: string;
                status: 'done' | 'failed' | 'skipped' }[];
failedItemId?: string;   // failed 时停在哪一项
```

**续跑**：管理端对 failed 任务点「续跑」（`POST /api/tasks/:id/resume`）→ 任务回 pending、
planProgress 保留（失败项之前的 done 不重做）、failedItemId 清除，员工新会话从失败项开始
（简报带之前各项结果摘要）。

**shadow 闸门**：现有 task_check 节点申报照常——shadow 级员工每项完成时申报、等人工放行，
放行后执行器才推进下一项；人工确认天然嵌在项与项之间，无新机制。

### 3. 能力注册表（后台可配置）

**数据模型**（`CapabilityDef`，file/sqlite 双 store，与 TaskStore 同模式）：

```ts
interface CapabilityDef {
  kind: string;          // 唯一键：'devops'
  name: string;          // 展示名：'发布部署'
  description?: string;
  tools: {
    builtin: string[];   // 内置能力：'bash' | 'files'
    mcp: string[];       // MCP 工具包：'forge' | 'deploy'
  };
  enabled: boolean;
}
```

- **预置 seed**：首次启动写入 dev/test/commit/devops（dev/test→builtin；commit→mcp:forge；
  devops→mcp:deploy），后台可改可停；
- **接入边界**：全新工具包（如未来 Jira MCP）第一次需一次代码接入（装配器注册
  "工具包标识→实例工厂"）；之后新增 kind、组合工具、启停、改映射全在后台配置，零代码零发版；
- **API**：`GET/POST /api/capabilities`、`PUT/DELETE /api/capabilities/:kind`（风格与 tasks/checks 一致）。

#### 3.1 首批注册的四类能力（详细定义）

**① `dev` — 开发编码**

| 项 | 内容 |
|---|---|
| name / description | 开发编码 / 阅读、编写、修改代码与文档，构建验证 |
| tools.builtin | `bash`（受 bashWhitelist 白名单约束）、`files`（工作区内文件读写） |
| tools.mcp | 无 |
| 依赖配置 | 无（基础能力，缺省 kind 即是它） |
| 典型任务项 | 开发接口与页面、写单元测试、修 bug、重构 |
| verify 建议 | `npm run build`（构建通过即产物可编译） |
| 失败语义 | 构建/编码验证失败 → 该项 failed，链停 |

**② `test` — 测试验证**

| 项 | 内容 |
|---|---|
| name / description | 测试验证 / 运行单元测试、e2e 测试并核对结果 |
| tools.builtin | `bash`、`files` |
| tools.mcp | 无 |
| 依赖配置 | 无 |
| 典型任务项 | e2e 测试某功能、回归验证、跑覆盖率 |
| verify 建议 | `npm test` / `npm run e2e`——**本类强烈建议必配**，测试结果以退出码为准，不采信员工口头"测试通过" |
| 失败语义 | 测试命令非零退出 → 该项 failed，链停（bug 回开发项时由人工续跑并调整计划） |

**③ `commit` — 代码提交**

| 项 | 内容 |
|---|---|
| name / description | 代码提交 / 建分支、提交文件、创建与查询 MR |
| tools.builtin | `files`（整理待提交产物） |
| tools.mcp | `forge`：`gitlab_create_branch` / `gitlab_commit_files` / `gitlab_create_mr` / `gitlab_get_mr` / `gitlab_get_file`（Gitea 适配层同构 `gitea_*` 五件套，按 yaml `forge.provider` 自动选择） |
| 依赖配置 | yaml `forge:` 段（provider/baseUrl/token）——未配置时分派即 fail fast |
| 典型任务项 | 提交到 feature 分支并建 MR 至 develop |
| verify 建议 | 提交类客观校验 = forge 工具调用返回（MR 创建成功返回 MR id/URL 即证据），执行器核对工具调用结果作为该项通过依据 |
| 失败语义 | forge 调用失败（认证失败/分支冲突/MR 创建失败）→ 该项 failed，链停 |
| 权限说明 | **放大权限项，必须显式声明 kind**——不声明 kind 的任务项永远拿不到 push 能力 |

**④ `devops` — 发布部署**

| 项 | 内容 |
|---|---|
| name / description | 发布部署 / 传输产物到目标环境并重启服务 |
| tools.builtin | 无（发布动作由 deploy 工具闭环执行，不开放裸 bash 给发布项） |
| tools.mcp | `deploy`：`deploy_to_env`（限 yaml 中显式配置的环境名）、`deploy_wait`（轮询至 done/failed） |
| 依赖配置 | yaml `deploy:` 段（envs[].name/artifactDir/restartCommand）——未配置时分派即 fail fast |
| 典型任务项 | 发布到测试环境并确认部署完成 |
| verify 建议 | `deploy_wait` 返回 done 即客观通过；任务项 detail 中应指明环境名与预期版本 |
| 失败语义 | 部署状态机 failed → 该项 failed，链停；重启脚本非零退出同判 |
| 权限说明 | **放大权限项，必须显式声明 kind**；环境白名单由 yaml 配置锁死，注册表再开放也超不出配置的环境列表 |

> 四类之外的新能力，走「能力管理」后台登记接入（见 §3 接入边界）。

### 4. 管理端 UI

- 新页面「能力管理」：列表（kind/名称/工具来源/启停开关）+ 新增/编辑表单（工具来源多选）；
- **任务创建双模式**：
  - **可视化配置**（新增）：表单式编辑任务包——基本信息（taskId/title/role/repo）、
    计划项逐条增删改排（id/kind 下拉[取自注册表，含缺省 dev]/title/detail/verify），
    kind 下拉只列 enabled 项；提交时生成任务包 yaml 走既有 `POST /api/tasks`，前端即配即校验；
  - **yaml 直贴**（现状保留）：直接粘贴/上传任务包 yaml 文本提交，满足熟练用户与批量场景；
  - 两种模式互导：可视化表单可由 yaml 反填生成，yaml 模式可从表单一键生成——同一数据源；
- 任务详情：计划进度条（每项状态徽标 done/failed/待执行，failed 高亮停点）+ failed 时「续跑」按钮；
- 现有 DAG 视图、节点验收队列不动。

### 5. 错误处理

| 场景 | 处理 |
|---|---|
| 任务包引用未注册/停用 kind | 创建任务时即报错（`任务项 t2.kind='devops' 未注册或已停用`），不入库 |
| 运行中注册表被改 | 该项执行时报错 → 按失败即停，留痕可续跑 |
| kind 依赖的 MCP 未配置（如 devops 但 yaml 无发布段） | 分派时 fail fast，报错指明缺哪段配置 |
| deploy 目标失败 | mcp-deploy 既有 failed 状态机映射为任务项失败，链停 |
| 过程留痕 | 每项开始/完成/失败 emit 事件进现有 EventBus/台账 |

### 6. mcp-deploy 接入执行链

`packages/mcp-deploy` 已有 `deploy_to_env` 与 `deploy_wait`（状态机 pending/deploying/done/failed）。

**本版本范围（收窄，用户明确）**：只做"**打包产物 → 目标服务器特定目录 + 重启服务/执行脚本**"：

- **发布动作**：把构建产物传输到目标环境配置的目录下，随后执行该环境配置的重启命令/脚本；
- **yaml 发布段**（每个目标环境一条）：

```yaml
deploy:
  envs:
    - name: test                      # 任务项 detail 里引用的环境名
      artifactDir: /opt/ddw/web-app   # 产物目标目录
      restartCommand: "bash /opt/ddw/restart.sh"   # 发布后执行（重启服务/脚本）
```

- `deploy_wait` 轮询至 done/failed，failed 映射任务项失败（链停）；
- 不接任何 DevOps 平台/流水线系统；行内将来要对接正式 DevOps 时再扩展。

### 7. 测试

- **runtime**：计划执行器单测——顺序执行、失败即停、续跑从失败项（前面 done 不重做）、
  工具集按 kind 切换、老 tasks 字符串格式兼容；
- **console-api**：CapabilityStore CRUD、seed 预置、任务包 kind 校验、resume 接口；
- **前端**：能力管理页、计划进度条、续跑按钮组件测试；
- **演示链路**：faux 注入 stream 跑 dev→test→commit→devops 全链。

## 不做的事（YAGNI）

- 不做跨员工流水线编排（用户确认用拆任务包 + dependsOn 覆盖）；
- 不做 DAG 拓扑排序/并行波次（现有 tick 全量扫描够用）；
- 不做失败自动重试（人工续跑，保守可控）；
- 不做能力注册表的版本化/审计日志（台账事件已覆盖过程留痕）。
