# 模型网关双协议兼容设计（OpenAI 端点 + Anthropic 端点）

日期：2026-09-05 ｜ 状态：已与用户对齐，待评审

## 背景与问题

`ModelGateway`（packages/runtime/src/model/gateway.ts）当前硬编码 `openai-completions` 协议：
`toPiModel` 固定 `api: 'openai-completions'`，`streamFnFor` 缺省注入 openai 的 `streamSimple`。
用户拿到的云端模型是**智谱 GLM Coding Plan**，其可用端点为 Anthropic 协议
（`https://open.bigmodel.cn/api/anthropic` + `glm-5.3-flash`，用户已自测可用），
OpenAI 兼容端点（普通 `/api/paas/v4`）对套餐报 1113 余额不足。

需求：**程序兼容两种协议，配置按路由选择**；不改用户端点形态。行内私有模型集群
（OpenAI 兼容）与云端套餐（Anthropic）未来并存，协议必须可按路由混配。

## 已确认的探索结论

- `pi-agent-core` 的 `StreamFn = (model: Model<Api>, context, options?) => ...` 本就协议无关。
- `pi-ai` 自带 `api/anthropic-messages` 适配器（`streamSimple`），与 openai-completions 同构。
- Anthropic 协议认证：`assertRequestAuth` 接受模型 headers 中的 `x-api-key`；
  `anthropic-version` 由 Anthropic SDK 默认补，无需显式配。
- executor / 调度器 / worker 只经 gateway 取 model 与 streamFn， fork 模式 routes 以 JSON
  IPC 原样透传——**消费方零改动**。

## 方案取舍

| 方案 | 说明 | 结论 |
|---|---|---|
| A. gateway 按协议分派 pi-ai 适配器 | ModelSpec 加 `api` 字段，toPiModel/streamFnFor 按协议切换 | **采用**（零自研协议代码） |
| B. 自写 Anthropic↔OpenAI 转换层 | 消息格式/流式事件互转，数百行易错代码 | 否（pi-ai 已有成熟实现） |
| C. 按 baseUrl URL 特征自动识别 | 配置最少但推断不可靠，端点改名即静默出错 | 否（用户已排除） |

协议字段粒度：**每条路由单独配**（用户选定）——primary 与 fallback 各自携带 `api`，
四条路由可混用不同协议端点，跨协议 fallback 自然可用。

## 设计

### 1. 配置形态

```yaml
routes:
  - callType: chat
    primary:
      api: anthropic-messages            # 新增可选字段：openai-completions（缺省）| anthropic-messages
      baseUrl: https://open.bigmodel.cn/api/anthropic
      apiKey: "..."
      model: glm-5.3-flash
```

老配置不写 `api` = 行为与现状完全一致（零回归）。

### 2. types.ts（packages/runtime/src/types.ts）

- `ModelSpec` 加 `api?: 'openai-completions' | 'anthropic-messages'`；
- 导出联合类型 `ModelApi` 供 gateway/config 复用。

### 3. gateway（packages/runtime/src/model/gateway.ts）

- `toPiModel`：`api: spec.api ?? 'openai-completions'`；
  - openai-completions → `headers: { Authorization: Bearer <key> }`（现状）；
  - anthropic-messages → `headers: { 'x-api-key': <key> }`（SDK 补 anthropic-version）；
  - `reasoning: spec.api === 'anthropic-messages'`（glm-5.3-flash 走 Anthropic 端点会回思考块，
    标记 reasoning 避免流式解析把 thinking 当正文；OpenAI 私有集群维持 false）；
- `modelFor` 返回类型放宽 `Model<'openai-completions'>` → `Model<ModelApi>`；
- `streamFnFor(callType, stream?, fallbackStream?)`：`stream` 缺省值由"固定 openai"改为
  **按路由 primary.api 选**对应 `streamSimple`；fallback 未显式注入时同样按 `fallback.api` 选。
  测试注入 fake stream 的能力不变（显式传入时覆盖缺省）。

### 4. 配置解析（packages/console-api/src/team/runtime-config.ts）

`parseRoute` 校验 `primary.api`（及 `fallback.api`，若存在）：可选、值必须是
`openai-completions | anthropic-messages` 之一，非法时报错可读
（`routes[0].primary.api 必须是 openai-completions/anthropic-messages 之一，得到 "xxx"`）。
doctor / 凭据解密（enc:v1:）链路零改动。

### 5. 消费方

零改动：executor / scheduler / process-executor / worker 不感知协议；
routes JSON 透传后新字段自动生效。

### 6. 测试

- runtime 单测（gateway.test.ts）：
  - 缺省不传 api → Model.api 为 openai-completions、Bearer 头（回归）；
  - `api: anthropic-messages` → Model.api 正确、`x-api-key` 头、reasoning=true；
  - streamFnFor 缺省按路由协议选适配器（用注入 fake 断言选路正确）；
  - fallback 自带协议时按 fallback.api 选缺省流。
- console-api 单测（runtime-config.test.ts）：parseRoute 的 api 校验
  （缺省通过 / 合法值透传 / 非法值报错可读）。
- e2e/演示链路（faux 注入 stream）不感知协议，无需改动。

### 7. 落地配置

`runtime-local.yaml`（不入库）四条路由改为：
`api: anthropic-messages` + `baseUrl: https://open.bigmodel.cn/api/anthropic` +
`model: glm-5.3-flash`（用户原始需求；Coding Plan 限定模型）。
`examples/console-runtime.example.yaml` 注释中补 `api` 字段说明。

## 错误处理

- 配置期：api 非法值在 `parseRuntimeConfig` 启动即失败（错误可读，带字段路径）——
  不带病运行，与既有校验风格一致。
- 运行期：协议错误（如端点 404/401）由 pi-ai 适配器按既有 stream 错误路径冒泡，
  executor 既有重试/事件记录不变。

## 不做的事（YAGNI）

- 不做 URL 自动识别；不做第三种协议（google-generative-ai 等 pi-ai 虽有，暂无需求）；
- 不做 per-请求协议切换；不动 doctor、UI、任务链路。
