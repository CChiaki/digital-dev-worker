## 1. 背景与问题诊断

大型企业（尤其银行）研发协同的核心问题：

1. **环境割裂**：Jira/禅道、GitLab、Jenkins、制品库、测试环境、Sonar、数据库各自为政，信息靠人搬运，上下文在交接中丢失。
2. **需求-开发断层**：需求单描述模糊，开发要反复确认；需求分析成果无法结构化传递给执行者。
3. **前后端联调损耗**：接口契约不先行，联调互相等待、来回返工。
4. **质量与合规人力黑洞**：单测、代码评审、发布材料、变更审批消耗大量人力，且是银行合规重灾区。
5. **存量维护占大头**：日常工作中大量是 Vue 页面 + Spring 接口的小颗粒变更，模式固定但琐碎。

**设计立场**：用一个"等同于正式员工"的全栈数字员工，寄生在客户现有工具链中，通过 MCP 服务矩阵把割裂的环境串起来，以固化任务包为接单单位，自主完成 需求理解 → 前后端开发 → 联调 → 测试 → 提交审核 → 测试发布 → 环境验证 全链路。

## 3. 总体架构

四个平面：

```
┌────────────────────────────────────────────────────────┐
│                   银行内网（完全离线）                     │
│                                                        │
│  割裂的存量环境：Jira/禅道 │ GitLab │ Jenkins │ 制品库     │
│                 测试环境(K8s/虚机) │ 数据库 │ Sonar       │
│        ▲ 每个环境封装为一个 MCP Server，统一暴露           │
│        │                                                │
│  ┌──────────────────────────────────────────────┐      │
│  │           MCP 服务矩阵（串起一切的中枢）          │      │
│  │  jira-mcp    gitlab-mcp   ci-mcp   deploy-mcp │      │
│  │  testenv-mcp db-mcp    sonar-mcp  browser-mcp │      │
│  │  （统一鉴权 · 全操作留痕 → 审计台账）              │      │
│  └──────────────────────────────────────────────┘      │
│        ▲ 工具调用                ▲ 事件流/介入            │
│  ┌────────────────────┐   ┌────────────────────┐      │
│  │ 数字员工运行时        │   │  轻量控制台          │      │
│  │ Agent 实例 × N      │   │  直播回放 · 介入对话  │      │
│  │ + 岗位 Skills       │   │  审计台账 · 员工档案  │      │
│  └────────────────────┘   └────────────────────┘      │
│        │ OpenAI 兼容协议                                │
│  模型平面：glm-5.3-flash / qwen3.8-27b（可路由可替换）     │
└────────────────────────────────────────────────────────┘
```

- **接入平面（寄生）**：数字员工在 Jira 是真实经办人、在 GitLab 是真实账号（独立分支、提 MR、回评论）。客户工具零改造。
- **运行时平面**：Agent 实例 + 工具网关（MCP 矩阵）。
- **控制台平面**：看（直播回放）、管（介入/暂停/接管）、审（审计台账）。
- **模型平面**：客户已有集群，OpenAI 兼容接入，按调用类型路由，可替换。

### MCP 服务矩阵

| MCP Server | 封装的环境 | 关键工具 |
|---|---|---|
| `jira-mcp` | Jira/禅道 | 接单、更新状态、写评论、查需求详情 |
| `gitlab-mcp` | GitLab | clone、建分支、push、提 MR、回评论 |
| `ci-mcp` | Jenkins/GitLab CI | 触发构建、读日志、取报告 |
| `deploy-mcp` | 发布系统/制品库 | 打包上传、申请部署到测试环境 |
| `testenv-mcp` | 测试环境 | 服务探活、读日志、查测试库数据 |
| `browser-mcp` | Playwright 沙箱 | e2e 测试、页面截图、联调自测 |
| `sonar-mcp` | SonarQube | 拉告警、修复核验 |

所有 MCP Server 统一鉴权、全操作留痕到审计台账。客户缺哪个环境的适配就补哪个 MCP，架构不变形。

**适配原则**：MCP 对外暴露的是工具契约，背后实现分两种——有 API/DevOps 集成的系统一期就一步到位用 API 适配器（如 GitLab、Jenkins/DevOps 平台、Sonar 自带 API）；没有 API 的系统先用 Playwright UI 垫片过渡。详见第 7 节。

### 岗位 Skills（技能库）

Markdown + 脚本形式挂载给数字员工：`联调SOP`、`Spring接口开发规范`、`Vue页面开发规范`、`单测编写规范`、`MR审核标准`、`测试发布流程`、`测试环境验证手册`。新项目经验沉淀为新 Skill。

## 4. 数字员工运行时内核

### 4.1 身份与进程结构

每个数字员工 = 运行时里一条**员工档案**（工号、姓名、技能清单、所属项目组、试用期状态）+ 一个常驻 Agent 进程：

```
Agent 实例（每员工一个）
├── 会话管理器     ← 长跑主循环：感知(事件) → 思考(LLM) → 行动(MCP) → 记录
├── 上下文装配器   ← 组装每次推理的上下文：员工档案 + Skills + 任务包 + 项目记忆
├── 模型路由器     ← 按调用类型路由 glm-5.3-flash / qwen3.8-27b，失败自动切换
├── 工作区         ← 独立沙箱/容器（见 4.7 执行层）：clone 目标仓库、可起 Vue dev server + Spring 服务
├── checkpoint     ← 每 N 步持久化：对话摘要 + 工作区快照引用 + 任务状态
└── 事件总线       ← 一切动作实时上报控制台（含人工介入注入点）
```

### 4.2 任务全链路

不设内部阶段闸门；执行序为 Agent 的默认 SOP，由 Agent 自主决定推进：

1. **接单**：从任务池领取任务包，`jira-mcp` 同步 Jira 状态为"处理中"
2. **现场勘察**：读文件清单涉及的代码、核对接口文档，产出轻量《执行计划》写回控制台
3. **后端开发**：Spring 接口 + DAO/Service 分层 + DTO，跑单测（自测通过才算完成）
4. **前端开发**：Vue 页面/组件；后端未完成时按接口契约 mock 联调
5. **联调自测**：本地起前后端，`browser-mcp` 走页面流程验证；后端用单测+接口测试覆盖
6. **提交审核**：独立分支 push、提 MR、写变更说明；导师在 GitLab Review（盯梢期硬闸门）
7. **测试发布**：按 `测试发布流程` Skill 打包、走 `deploy-mcp` 部署到测试环境
8. **环境验证**：`testenv-mcp` 探活 + `browser-mcp` 在测试环境复走核心路径 → 结果写回 Jira、流转状态

> **落地勾稽（P5）**：1–8 的工具链已全部交付（`@ddw/mcp-gitlab`/`mcp-jira`/`mcp-ci`/`mcp-deploy`/`mcp-testenv`/`mcp-browser` + 工作区编码工具），全链路闭环 e2e 已验证：接单→编码→自测→commit→MR→Jira→构建→部署→验证环境探活→汇报，14 个 tool_call 按序留痕。

**执行模式定稿（2026-09-04 补充）：目标驱动 + 清单式软编排，非固定模式也非编排引擎**

| 模式 | 做法 | 判定 |
|---|---|---|
| 固定模式 | 引擎按预定义流程推进，每步产物格式固定 | ✗ 代码任务变化多，模型被流程卡死，无返工弹性 |
| 编排模式 | DAG 引擎按任务图调度节点间产物传递 | ✗ 一期单员工全栈单体，引擎是过度设计；节点粒度太粗，模型价值恰在节点内部 |
| **目标驱动 + 清单软编排（本方案）** | 任务包定义 what+why（目标/文件清单/验收标准），执行序 1–8 仅是 SOP 提示词；模型自主决定推进顺序、串并行、何时返工 | ✓ spec 本节现状 |

关键：任务包 `tasks: [T-1, T-2…]` 是**给模型的检查清单（checklist），不是给引擎的调用图**——模型逐项推进、逐项跑 acceptance 自测、不通过即返工，顺序可依现场发现而变（这正是固定编排做不到的）。

**真编排的引入时机（二期团队化）**：前端/后端/测试员工协作时，班组调度按**任务包之间的依赖声明**（T-2 依赖 T-1 产物）分配，而非节点级 DAG。一期的"单体员工 + 清单模式"正是铺路：**任务包边界 = 未来编排的最小单元**。二期班组化的编排信号用任务节点 checkpoint 事件（见 4.4 节尾）。

### 4.3 任务控制台与任务包（固化任务）

需求分析阶段以**任务包**形式固化。示例：

```yaml
jira_ref: BANKAPP-8823            # 溯源：来自哪个需求单
title: 客户管理列表增加按行业筛选
repo: http://gitlab.bank.local/crm/crm-web        # 代码仓库
branch: feature/crm-industry-filter               # 工作分支（自动建）
files:                                            # 细化到文件级
  - src/views/customer/list.vue
  - src/api/customer.ts
  - src/store/modules/customer.ts
acceptance:                                       # 可验证的验收标准
  - 列表页新增行业下拉筛选，支持多选
  - 筛选后分页重置到第 1 页
  - e2e: 走通 筛选→查询→清空 流程
docs:                                             # 接口文档地址
  - http://wiki.bank.local/crm/api/customer-list-v2
constraints: { deadline: 2026-09-05, reviewer: 张工 }
skills_required: [vue-开发规范, 联调SOP]
```

任务控制台（控制台的一个模块）：

- **任务池视图**：任务包按项目/优先级/技能要求分组，状态：待领取/执行中/待审核/已交付/已打回
- **接单模式**：数字员工按技能清单自行动领取匹配任务；支持指派模式
- **固化工作台**：导师从 Jira 需求生成任务包草稿 → 补文件清单/验收标准 → 发布进任务池（三期做固化辅助自动化）
- **打回重做**：审核不通过回到池中附打回意见，原员工优先再领

### 4.4 人类盯梢与介入

- **直播**：控制台实时显示事件流（思考摘要、工具调用、diff 预览、测试结果）
- **介入三档**：💬 发消息指导（下轮推理注入）/ ⏸ 暂停 / ✋ 接管（人工改完交还）
- **盯梢期策略**：试用期所有 MR 必须人工批准、部署操作走 `deploy-mcp` 二次确认；转正后按项目粒度配置放权（如"单测全绿+lint 通过的 MR 自动合入"）

**节点产物审核定稿（2026-09-04 补充）：三级闸门，非"每节点人审"也非"全后审"**

切分依据是**错误的发现成本**——越早发现越便宜：

| 层级 | 谁审 | 卡在哪 | 落地现状 |
|---|---|---|---|
| ① 机器审（节点内） | 可执行验证：单测/构建/lint/e2e | 每个 task 项完成时，acceptance 不通过不进下一项（**节点审核主力，零人力**） | ✅ acceptance 进任务简报 + 自测跑通才提交 |
| ② 人工硬闸门（出口） | 导师/业务人 | 只设不可逆或对外可见的边界：MR 合并（盯梢期硬闸门）、部署（prod 已被工具层禁止） | ✅ 流程已定（4.2 第 6 步），工具已支持 |
| ③ 事后审计（兜底） | 审计台账 | 全节点过程留痕（thinking/tool_call/diff），可回放可追责，盯梢期人工抽检 | ✅ 事件流 + audit v2 任务级时间线 |

**盯梢成熟度模型**：随信任等级移动的只有②的收紧程度，①永远不变：

```
盯梢期：机器审全跑 + MR 全人审 + 人盯直播      ← 一期现状
半成熟：机器审全跑 + MR 抽审（如 30%）+ 台账日检
成 熟：机器审全跑 + 事后审计为主
```

**放权配置化（2026-09-04 补充定稿）**：信任等级是数字员工身份的显式属性 `SupervisionPolicy.level`（`shadow` 盯梢 / `assisted` 辅助 / `trusted` 信任），一级一语义、生效点有限而明确：

| 生效点 | shadow（盯梢期，默认） | assisted | trusted |
|---|---|---|---|
| bash 白名单 | 仅任务基线白名单（git/node 等） | 同 shadow | 基线 + policy 放行的额外命令（如 git push） |
| 黑名单拦截 | 全开（不可放权） | 全开 | 全开（**黑名单永不放权**） |
| 任务开始留痕 | 事件流记录 `盯梢级别: shadow` | 同左 | 同左（审计可查当时等级） |
| MR 合并 | 全人审（GitLab 端流程闸门） | 抽审（GitLab 端配置） | 可配自动合入条件（GitLab 端配置，runtime 只留痕） |

原则：**runtime 只管"能执行什么"（bash 白名单派生 + 黑名单永全开），MR/部署的流程闸门留在 GitLab/DevOps 平台端配置**——放权不造新的执行点，只把"当时等级"写进审计，事后可追责。

**节点 checkpoint 事件（P6 候选，已登记）**：当前"节点完成"无显式事件，审计只能从工具调用序列推断。规划为：每个 task 项完成时 emit `task_check` 事件（项 id + acceptance 执行结果 + diff stat）——审计 timeline 渲染"清单打勾"视图（人审 MR 时逐项看机器审证据）、盯梢直播节点推进可视化、二期班组编排以它为"上游产物就绪"信号。实现薄：runtime 执行循环按 tasks 项 emit，不动架构。

### 4.5 失败恢复

中断（进程崩、模型超时、环境挂）→ 从最近 checkpoint 恢复：重建会话摘要 + 复用/重建工作区 + 校验未完成动作（如 MR 是否已提过），继续推进而非重做。

### 4.6 Agent 内核选型：pi（✅ 已定稿：P0 验证 GO，P1 封装层已交付）

> **定稿记录（2026-09-04）**：P0 七项验证全部通过（`packages/spike-pi/VERDICT.md`，锁版 0.84.4）；P1 按封装层计划交付 `@ddw/runtime`（ModelGateway / ToolRegistry+pi 适配 / 安全拦截层 / 任务级 session / EmployeeRuntime），20 用例全绿，验收记录见 P1 计划文档「执行记录与验收结果」。关键架构事实：pi-agent-core 的 AgentHarness 为未实现脚手架、AgentSession 过度耦合——产品层定为**裸 Agent + Session 手工接线**。

执行内核采用开源 pi agent harness（badlogic/pi-mono，MIT，TypeScript），**只取其下两层**（`pi-ai` 模型层 + `pi-agent-core` 运行时层，SDK 模式嵌入运行时），不用其终端 CLI 壳。选型理由与已确认的匹配点（★=P0/P1 已实测确认）：

- **协议兼容**：内置"任意 OpenAI 兼容 API"（Ollama/vLLM/LM Studio）——行内私有化模型直连零适配；非标准网关协议可用 `createProvider()` 自定义 provider 做协议转换扩展（协议转换是 pi 原生扩展点，不需要外挂网关）
- **按调用类型路由模型**：模型是每次调用的参数（`stream(model, context)`），且支持 cross-provider handoffs（会话中途换模型）——chat 用 glm、code 用 qwen 的路由天然支持
- **工具拦截钩子**：`beforeToolCall`/`afterToolCall` 可拦截、阻止工具执行——审计台账留痕与盯梢期敏感操作审批（部署类工具拦截等人工放行）的原生挂载点
- **事件流**：`agent.subscribe()` 完整生命周期事件（思考、工具执行起止）——控制台直播的映射源
- **人类介入**：steering 机制支持任务运行中注入消息——"导师发消息指导/纠偏"是原生能力，无需自建注入通道
- **会话持久化**：JSONL session（含分支 branching、上下文压缩 compaction）+ SQLite backend——任务级 checkpoint/resume 基于它封装
- **多实例**：Agent 为普通类实例，单进程多员工并行 + `waitForIdle()` 并发管理
- **天然全自动**：pi **无内置权限确认系统**，默认无任何人工弹窗——Claude Code 系 agent 需先拆权限确认才能无人值守，pi 天生即全自动形态，零接入成本。管控由此转移到工程期配置（每员工独立容器、网络出口白名单、工作区路径白名单、bash 命令黑名单、凭据最小化）+ 运行期审计（beforeToolCall 拦截层 + MCP 网关留痕），人工介入仅为可选的观测与纠偏手段（直播/发消息/暂停），不是流程中等待人的环节

**已知风险与处置**：pi 无权限系统 → 容器化+白名单+拦截层兜底（官方提供容器化文档）；上游强个人风格演进（新贡献者 PR 默认关闭）→ 锁定精确版本，MIT 可 fork 兜底；依赖准入走行内供应链审计，必要时 review 改造后入库。P0 验证通过后本节定稿，未通过则回退自研内核（另见 P1 自研计划）。

### 4.7 工作区执行层：OS 沙箱先行，容器收口（2026-09-04 补充定稿，✅ P5 落地）

数字员工执行 bash 的防线分两层：**工具层软防线**（P4 已落地：白名单 → 黑名单 → 禁链式 → 无 shell 分词）+ **执行层硬防线**。硬防线的演进路径定为：

```
阶段一（试点/开发机）：OS 沙箱（bubblewrap / landlock）   ← 无需特权 daemon，即时可用
阶段二（生产容器平台）：Docker / 行内容器平台（Harbor 镜像）← 最终方案
```

**演进依据**：容器（Linux）本质 = mount/PID/network namespace + cgroups + 联合文件系统，与 OS 沙箱是同一批内核原语；差别是"自拼原语"还是"用打包产品（附镜像生态）"。两者对数字员工的三项核心防护能力对等：

| 防护项 | OS 沙箱（bwrap/landlock） | 容器（Docker/K8s） |
|---|---|---|
| 文件系统越界（只读根 + 工作区唯一可写） | `--ro-bind / --bind /workspace` | `--read-only -v ...:rw` |
| 网络外联 | `--unshare-net`（物理断网）或白名单代理 | `--network` 白名单 / 网络策略 |
| 资源滥用（fork 炸弹/内存吃满） | cgroups v2 限额 | cgroups 限额 |
| 环境一致性（JDK/Node 版本钉死） | ❌ 依赖宿主机环境（**主要短板**） | ✅ 镜像即环境 |
| 部署门槛 | ✅ 无特权、无 daemon、无镜像分发链 | 需容器 daemon/平台 + Harbor 审批 |
| 状态清理 | ✅ tmpfs + 每任务独立工作区，即弃 | ✅ 可写层即弃 |

**决策**：试点期机器拿不到 Docker daemon/root 权限时用 OS 沙箱（可行性已论证）；生产收口到容器（环境一致性 + 平台化配额 + 镜像统一管理是银行合规刚需）。**不是二选一，是分阶段递进 + 并存兼容**。

**兼容中间层**：不需要为两种方案各写一套逻辑——P4 已落地的契约层即中间层，只需在其下增加一个 `SandboxBackend` 抽象（P5 实施）：

```
ControlledBash（软防线：白名单/黑名单/禁链式/引号分词，不变）
        │ exec(cmd)
        ▼
SandboxBackend（硬防线中间层，新增）
├── NoopBackend        本地直跑（开发/单测，现状）
├── BwrapBackend       bwrap/landlock 包装 argv（试点机）
└── DockerBackend      docker exec 包装（生产平台）
```

三个实现都只是"把原命令翻译成沙箱内 argv"，工具层、Workspace 接口、模型侧完全无感；按部署机器条件选择 backend（配置一项即切换）。镜像侧同步收口为两个基础镜像：`agent-env:java17`（Spring 线）、`agent-env:node20`（Vue 线），外网构建 → Harbor/离线导入。

## 5. 控制台与审计设计

### 5.1 模块清单

| 模块 | 功能 |
|---|---|
| 任务中心 | 任务池 / 固化工作台 / 任务包详情 |
| 员工中心 | 员工档案、实时事件流直播、介入对话、历史任务 |
| 审计中心 | 全操作台账、MR/部署审批记录、任务回放器 |
| 系统管理 | MCP 注册与健康、模型路由配置、放权策略配置 |

### 5.2 数据模型（核心六张表）

```
employee(员工档案) ─┬─ task(任务包) ──┬─ event(事件流)      ★回放最小单位
                    │                 ├─ artifact(工件)     执行计划/diff/测试报告/截图
                    │                 └─ intervention(介入)  消息/暂停/接管/审批
mcp_service(MCP注册) ─ audit_log(审计台账)   ★所有 MCP 调用的权威留痕
policy(放权策略)
```

**存储中间层定稿（2026-09-04，二期第 1 步）：业务端只依赖 Store 接口，换库零改造**

与 7.1 transport 注入同一原则，固化到数据面：

```
业务端（handlers / runtime 调用方 / 前端 API）
        │  只依赖接口
   TaskStore ──────────────┬── FileTaskStore     （文件 JSON，测试 Fake / 极简部署）
   EventStore              ├── SqliteTaskStore  （node:sqlite 内置驱动，试点默认）
        │                  └── MySqlTaskStore    （生产规模化时新增，业务端零改动）
   （同名接口，实现可替换，选择 = 组装处注入一行）
```

- **驱动**：`node:sqlite`（Node 内置，零依赖零编译，契合控制台"零运行时依赖"原则；内网离线免装包）
- **session JSONL 不迁**：流式追加的 checkpoint 性质，与 pi 格式契合，不属于审计范围，保留文件形态
- **audit 不可篡改**：event/audit 表逐条记录 `prev_hash` + 本条 `hash`（对内容+前条哈希做 SHA-256），链头定期快照归档，满足 5.4 合规要求
- **迁移 MySQL 的触发信号**：数字员工跨机器多实例部署（文件锁瓶颈）、行内要求审计数据集中管控、多年期数据量级。届时只新增实现类 + 组装处换注入，业务端与测试（contract 测试对全部实现各跑一遍）零改动

### 5.3 直播与回放

- 事件分级：`thinking`（思考摘要）/ `tool_call`（参数与结果摘要）/ `diff`（文件变更）/ `report`（测试结果、截图）；WebSocket 推送
- **落地勾稽（P5）**：v1 以 SSE 直播交付（`GET /api/events/stream`，at-least-once 增量 + id 幂等去重，比 WebSocket 更贴合银行内网单向直播场景）；回放由 `GET /api/audit/:taskId` 任务级时间线承担
- 回放器：按 event 时间轴回放，diff 并排对比、截图逐帧看；复核已完成任务 ≈ 看录像
- event 表与 audit_log **分开存**：前者服务理解，后者服务合规（不可篡改、完整 MCP 参数、保留期按银行要求）

### 5.4 审计台账

四类记录：MCP 调用、敏感操作（git push/部署/执行 SQL，无论成败）、人工介入、模型调用（员工/任务类型/模型/token 成本）。带 `jira_ref / task_id / employee_id` 三重关联，可从 GitLab MR 一路追溯到任务包、事件流、审批人。
**落地勾稽（P5）**：任务级聚合视图 `GET /api/audit/:taskId` 已交付（task 状态 + 全量 timeline + toolCalls 调用/错误计数 + 最终回复），四类记录的合规化落库（不可篡改、保留期）随二期数据库化推进。

## 6. 落地路径

### 一期 · 走通单任务全链路（6–8 周）

最小闭环：1 个数字员工 + 1 个试点项目 + 人工固化任务包。

| 周 | 内容 |
|---|---|
| 1–2 | `gitlab-mcp` + `jira-mcp` + 模型路由器；Agent 内核（会话主循环 + checkpoint）；工作区容器（clone + 构建 + 单测） |
| 3–4 | 后端链路：Spring 接口 + 单测自测 + 建分支提 MR；`ci-mcp` 对接行内 DevOps 平台（触发构建 + 等待结果）；任务包模型 + 控制台任务中心（池视图 + 接单） |
| 5–6 | 前端链路：Vue 页面 + `browser-mcp` e2e；联调自测；事件总线 + 直播页 |
| 7–8 | `deploy-mcp` + `testenv-mcp`：测试发布 + 环境验证；介入对话（发消息/暂停）；审计台账 v1。**端到端演示** |

### 二期 · 盯梢成熟 + 团队化（4–6 周）

固化工作台（任务包模板）、回放器、接管模式、放权策略（转正机制）、`ci-mcp`/`sonar-mcp`、多员工并行领包、模型路由精细化。

### 三期 · 需求分析自动化（迭代）

基于任务包固化历史数据，做"Jira 需求 → 任务包草稿"自动生成，导师只修订。需求分析自动化放在有数据积累之后。

### 试点方案

- **选点**：1 个 Vue + Spring 中小型系统，任务以列表页 CRUD + 接口开发为主
- **人员**：1 名导师（盯梢+固化）+ 1 名数字员工，试点期 4 周
- **成功判据**：≥ 10 个任务包端到端跑通；全程留痕可回放；平均单任务人工介入次数呈下降趋势
- **风险预案**：
  - 模型能力不足 → 收窄任务包粒度（文件清单更细）
  - 测试环境不稳定 → `testenv-mcp` 重试与降级（本地验证替代）
  - 银行安全评审 → 敏感操作全走 MCP 网关留痕，一期即上审计台账

## 7. MCP 实现策略：契约/适配分离 + UI 垫片

### 7.1 核心原则

**Playwright 只是 MCP 的临时适配层，不是数字员工的工具；后期由各系统改造提供标准 MCP/API 服务，届时只换适配层实现，工具契约与数字员工零改动。**

```
数字员工（只认工具契约，永远不变）
   │  jira.search / jira.update_status / gitlab.create_mr / ci.trigger_build ...
   ▼
MCP Server（对外暴露统一的工具契约）
   │
   ▼
适配层（同一工具，两种实现，可切换）
   ├── API 适配器：REST/SDK 直连（快、稳、首选，一步到位）
   └── UI 适配器：Playwright 模拟用户登录操作（慢、脆、临时兜底）
```

### 7.2 构建链路（行内 DevOps 平台已对接好的部分）

构建发布链路前期已由行内 DevOps 平台打通，数字员工不做构建编排，只做三步：

1. **提交代码/合并分支**：push 到工作分支（`gitlab-mcp`）
2. **触发构建任务**：在 DevOps 平台上触发对应构建任务（`ci-mcp`；平台有 API 则 API 适配，无则 Playwright 垫片）
3. **等待结果**：平台自动拉取分支代码、编译、打包，`ci-mcp` 轮询/回调等待构建结果并回读日志

### 7.3 UI 适配器（Playwright 垫片）设计要点

**凭据与登录**

- 每个数字员工在目标系统有独立真实账号（等同正式员工），凭据托管在 MCP Server 凭据库（对接行内密码保险箱，一期加密配置）
- 登录态持久化：Playwright storageState 按员工×系统缓存，session 过期自动重登
- 试点系统选型排除项：验证码（选无验证码或行内白名单系统）、SSO 跳转、短信/UKey 二次认证（硬阻断，必须排除）

**执行顺序管理（2026-09-04 定稿）：不写"脚本"，写"剧本"**

UI 自动化工具的传统做法是把"点哪→填什么→下一步"固化为脚本（YAML/代码），带来脚本库膨胀、UI 改版即断、更新须发版三大问题。本方案中**执行顺序由 Agent 运行时生成，不预先固化**：

- **原子动作层**：`mcp-browser` 只提供 `browser_navigate / click / fill / get_text / screenshot` 等稳定原语（浏览器原语极少变），执行顺序由模型看着页面内容现场决策——页面改版模型自适应，天然自愈，**无脚本可腐化**
- **剧本层（SOP）**：业务流程以**自然语言步骤清单**沉淀在岗位 Skills 或任务包 `requirement/acceptance` 字段（如"登录→进报销管理→核对首行金额与单据一致"），不写选择器级指令；SOP 跟 git 版本化，更新 = 改一段 markdown 走 MR（导师/业务人员可直接改），非代码发版
- **失败自愈闭环**：垫片报可读错误（含当前页面实际元素）→ 模型自纠偏改道（事件流留痕，盯梢人可见）→ 仍失败则截图 + 失败原因 → 任务 failed → 人工看截图判断 SOP 过时或真 bug → 改 SOP（MR）→ 下次任务自动生效。**"失败事件→审计留痕→人工改 SOP→git 版本化"就是更新机制本身**，无需独立脚本更新流水线
- **高频路径的终态不是录制固化，而是 MCP 化**：某流程调用频次高到值得优化时，正确动作是**推动该系统提供标准 MCP/API 服务**（回归 7.4 三期方向），Playwright 垫片随之退役——而不是把剧本"录制固化"成回放脚本固化在垫片里。录制固化（record & replay，YAML 存语义步骤非选择器，失败自动降级模型自由走查）仅作为**三期前的过渡优化**保留，且优先级低于推动 MCP 化

**稳定性**

- 选择器集中管理，页面改版只改一处
- 适配器自带愈健康检查：定期冒烟（如打开列表页），失败告警控制台并标记不可用
- 操作幂等：UI 操作前先读状态（如 Jira 单是否已是"处理中"），避免重试造成重复操作

**性能与并发**

- UI 适配只用于低频写操作和状态同步（接单、更新状态、写评论）；高频/大流量操作走原生通道
- 每个适配器在 MCP 注册表标注实现类型（api / ui），垫片覆盖范围一目了然

**审计合规**

- UI 操作同样过 MCP 网关留痕，附加截图 + DOM 快照作为证据，比 API 调用更可审计
- 数字员工账号在行内系统的操作日志与真人员工同等可查

### 7.4 迁移路径（三步走）

| 阶段 | 适配形态 | 动作 |
|---|---|---|
| 一期 | API 优先 + UI 垫片兜底 | GitLab/Jenkins(DevOps)/Sonar 等自带 API 的系统一期即 API 适配器一步到位；Jira/禅道、老发布系统等无 API 的"钉子户"用 Playwright 垫片 |
| 二期 | 混合 | 更多系统切 API 适配器；向行里提交系统改造需求清单（按调用频次和稳定性痛点排序） |
| 三期+ | 系统 MCP 化 | 行内系统逐个提供标准 MCP/API 服务，只换适配层，工具契约与数字员工零改动 |

> **垫片退役原则（2026-09-04 补充定稿）**：Playwright 垫片是**低版本兼容的短期目标**，不是终态。判定某个 UI 垫片"该退役"的信号就是它的调用频次——高频流程（如每日多次的构建查询、状态同步）优先列入向行里提交的 MCP 化改造需求清单（7.4 二期动作），改造完成后垫片下线；低频流程（月度级运维操作）垫片可以长期存在。也就是说：**高频 = 推动 MCP 服务化，低频 = 垫片兜底**，录制固化脚本只是两者之间的过渡态，不作为能力沉淀方向。

## 8. 范围外（明确不做）

- 生产环境发布与验证（一期只到测试环境）
- 需求分析全自动（三期才做辅助固化）
- 非 Vue/Spring 技术栈（一期聚焦单栈跑通全链路。**扩展路径**：换栈不是模型能力问题——30B+ 模型对各主流语言均有基础能力；边际成本在工程侧三件事：① 新栈 Skills（编码规范/联调SOP/发布流程，规范多数不在代码里而在 wiki 与评审惯例中，需人工沉淀）；② 工具链适配（构建/单测/e2e 命令通路、工作区容器适配）；③ 新栈任务包模板。内核、任务包体系、控制台、MCP 矩阵全部复用，二三期按客户项目需要逐栈扩展）
- 多角色数字班组协作（用户已选全栈单体）
- 私有化部署交付形态适配（产品先在自有环境开发，交付适配后置）
