# P8 · 二期第 2 步：班组并行与依赖编排（2026-09-05）

**Goal**：落实 spec 4.2「真编排引入时机」与 D2-D3 决策——**单进程多 EmployeeRuntime**（D2：试点期不做进程级隔离）+ **任务包级 `dependsOn` 依赖声明**（D3：yaml 起步，非节点级 DAG）+ **岗位标签匹配**。上游任务包 done = 下游就绪；无依赖的任务包并行分派；任务包边界 = 编排最小单元。

**决策依据（用户已拍板）**：D2 试点期单进程多 runtime；D3 依赖声明 yaml `dependsOn` 起步；D4 数据库化（P7 已交付）。

## 设计边界（先定死，防过度设计）

| 决策点 | 定稿 | 理由 |
|---|---|---|
| 依赖粒度 | **任务包级**（taskId 引 taskId），不做节点级 DAG | spec 4.2 定稿：任务包边界 = 编排最小单元，节点内部是模型价值区 |
| 调度与执行分离 | `TeamScheduler` 只做**分派决策**（纯函数 + 可测）；执行拉起是注入的 `executor` 回调 | 调度逻辑可 TDD；员工运行时组装（workspace/工具/盯梢）不掺进调度 |
| 员工名册 | 配置化 `EmployeeRoster`（id/name/role/supervision），不进数据库 | 试点期员工数量个位数，yaml/代码配置够用；档案化留后续 |
| 岗位匹配 | 任务包 `role`（单值）∈ 员工 `skills`（数组）才可分派；无 role 的任务包任意员工可接 | 最小语义；多标签需求出现再加 |
| 依赖语义 | dependsOn 全部 `done` → ready；任一 `failed` → blocked（不可自动恢复，等人工处理） | 失败传播保守取向：上游产物有问题，下游不该跑 |
| 并发模型 | 单进程内 Promise.all 并行 executor；员工工作区按 employeeId 隔离目录 | P0 spike s5 已验证 pi 多实例不串扰 |
