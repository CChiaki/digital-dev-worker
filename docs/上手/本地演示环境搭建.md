# 本地演示环境搭建（云端模型 + 本地 Gitea 跑通完整开发任务）

> 目标：在本机（或一台内网虚拟机）跑通一个**完整链路**的开发任务——
> 调度分派 → 数字员工编码 → **提交分支/Commit/MR 到本地代码托管（Gitea）** → 节点申报 → 人工放行 → 汇报。
>
> 拓扑：
>
> ```
> 管理端(5173) ──► console-api(3100) ──► 云端大模型（OpenAI 兼容端点，你提供 baseUrl + key）
>                         │
>                         ├─► 数字员工工作区（./workspace，本地文件编码工具 + 受控 bash）
>                         └─► 本地 Gitea(3000)（gitea_* 协作工具：建分支/提交文件/建 MR）
> ```

## 0. 前置清单

| 项 | 要求 | 说明 |
|---|---|---|
| Node.js | ≥ 20.5（node:sqlite） | `node -v` |
| pnpm | 任一近期版本 | 仓库根 `pnpm install` 已做过可跳过 |
| 云端大模型 | OpenAI 兼容端点 + API key | 一个端点即可，四类路由（chat/code/review/test）都指向它 |
| 本地 Gitea | 建议 ≥ 1.20 | 多文件单 commit 走 change_files；旧版本自动回退逐文件提交（功能不受影响，仅 commit 数变多） |
| 构建产物 | `packages/console-api/dist/` 已构建 | 构建命令见步骤 1（由你自行执行） |

> 本文档所有"启动/构建"命令均**由你在自己终端执行**。

## 1. 构建与加密主密钥（一次性）

```bash
# 仓库根
pnpm install
pnpm -r build          # 或最小集：pnpm --filter @ddw/runtime --filter @ddw/mcp-gitlab --filter @ddw/console-api build

# 凭据主密钥（可选但推荐：token/apiKey 用密文落盘，yaml 可进 git）
node packages/console-api/dist/cli.js cred key        # 输出一行 base64，注入环境变量
export DDW_CRED_KEY="<上一步输出的密钥>"
node packages/console-api/dist/cli.js cred enc "<你的云端模型key>"     # 产出 enc:v1:... 粘进 yaml
node packages/console-api/dist/cli.js cred enc "<你的Gitea PAT>"       # 同上
```

明文直接写 yaml 也能跑（doctor 对明文配置不阻塞），首次跑通后建议再换密文。

## 2. 本地 Gitea 准备

### 2.1 启动（Docker，已装可跳过）

```bash
docker run -d --name gitea -p 3000:3000 \
  -e GITEA__server__ROOT_URL=http://localhost:3000 \
  gitea/gitea:1.22
# 首次访问 http://localhost:3000 完成安装（数据库选 SQLite 即可）
```

### 2.2 建仓库与基线分支

1. 新建组织（如 `demo`）+ 仓库（如 `web-app`）→ 地址即 `http://localhost:3000/demo/web-app`；
2. 仓库初始化一个空 commit（Gitea 界面"初始提交"或本地推一个 README）；
3. **建基线分支 `develop`**（Gitea 网页：分支下拉 → 新建分支 `develop`）——MR 目标分支用它；
4. 建 Personal Access Token：**头像 → 设置 → 应用 → 生成新令牌**，勾选 **repository（read + write）** scope。

```bash
# 验证 PAT（应返回你自己的用户信息）
curl -H "Authorization: token <PAT>" http://localhost:3000/api/v1/user
```

> 数字员工的仓库标识由任务包 `repo.url` 自动推导：`http://localhost:3000/demo/web-app.git` → `demo/web-app`。

## 3. 运行时配置 yaml

复制 `examples/console-runtime-demo.yaml` 为 `runtime-local.yaml`，按下面改（关键三处：routes 指向云端端点、forge 段打开、workspaceRoot 留默认）：

```yaml
profiles:
  - id: demo-backend
    name: 小数
    role: backend
    skills: [backend, test]  # 兼容保留（2026-09-08 起调度按 role 精确匹配，skills 不再参与分派）
    supervision:
      level: shadow          # 节点申报阻塞等人工放行（演示亮点）
  - id: demo-frontend
    name: 小智
    role: frontend
    skills: [frontend]
    supervision:
      level: shadow

routes:
  - callType: chat
    primary: { name: 主力, baseUrl: "<云端端点，如 https://api.xx.com/v1>", apiKey: "<key 或 enc:v1:...>", model: "<模型名>" }
  - callType: code
    primary: { name: 代码, baseUrl: "<同上>", apiKey: "<同上>", model: "<同上>" }
  - callType: review
    primary: { name: 评审, baseUrl: "<同上>", apiKey: "<同上>", model: "<同上>" }
  - callType: test
    primary: { name: 测试, baseUrl: "<同上>", apiKey: "<同上>", model: "<同上>" }

workspaceRoot: ./workspace
sessionsRoot: ./sessions
tickIntervalMs: 3000
bashWhitelist: [git, node, npm, npx, python3]

# 代码托管协作（本次新增能力）：配置后员工获得
# gitea_create_branch / gitea_commit_files / gitea_create_mr / gitea_get_mr / gitea_get_file
forge:
  provider: gitea                  # 本地装的是 Gitea；GitLab 填 gitlab（附录 A）
  baseUrl: http://localhost:3000   # 服务根地址，API 前缀 /api/v1 自动拼接
  token: "<PAT 或 enc:v1:...>"
```

### 3.1 存储配置（可选）

不配 `storage:` 段 = sqlite（`<data>/ddw.sqlite`），本演示无需改动。想体验 MySQL 存储（存储企业化，
需本地已有 MySQL）在 yaml 追加：

```yaml
storage:
  driver: mysql
  mysql: { host: 127.0.0.1, port: 3306, user: root, password: "<明文 或 enc:v1:...>", database: ddw }
```

库须预先 `CREATE DATABASE ddw;`（表首次启动自动建）。旧形态存量数据（sqlite 任务/事件 + JSON 档案）
迁移：`node packages/console-api/dist/cli.js migrate --runtime runtime-local.yaml`（目标非空即拒绝，
marker 留痕，源文件不动）。

## 4. 巡检（不起服务，不占端口）

```bash
node packages/console-api/dist/cli.js doctor --runtime runtime-local.yaml --probe
```

期望：Node 版本 / 数据目录 / 存储审计链 / 运行时配置与凭据 / bash 白名单 / **模型集群连通（--probe 会实际访问云端端点）** 全部 ✓。

## 5. 启动与提交任务

### 5.1 启动（你自己的终端执行）

```bash
node packages/console-api/dist/cli.js --runtime runtime-local.yaml --port 3100
# 另开一个终端：管理端
cd apps/console && npx vite --port 5173        # 访问 http://localhost:5173
```

### 5.2 任务包（指向本地 Gitea）

复制 `examples/demo/task-backend.yaml` 改 repo 段（前端包同理）：

```yaml
taskId: TASK-DEMO-001-BACKEND
title: 消息通知服务端接口（本地演示：盯梢放权）
role: backend
repo:
  url: http://localhost:3000/demo/web-app.git   # ← 指向本地 Gitea；仓库标识自动推导为 demo/web-app
  branch: feature/demo-backend
  baseBranch: develop                            # ← 前面在 Gitea 建好的基线分支
tasks:
  - id: T-1
    title: 通知接口开发
    files:
      - src/api/notification.ts
    requirement: 实现站内信通知接口，按 apiDocs 契约返回
    acceptance:
      - 接口自测通过
      - 节点验收清单逐项确认
reportChannel: 完成后在 MR 描述附演示说明
```

### 5.3 提交与放行

1. 管理端「任务中心」→ 粘贴任务包 yaml 提交（等价 `curl -X POST localhost:3100/api/tasks --data-binary @task-backend.yaml`）；
2. 调度器按岗位分派给小数 → 「员工直播」看实时事件流（思考/工具调用）；
3. 员工走到节点申报（task_check）→ shadow 级阻塞 → 「节点验收」页**人工放行**；
4. 员工继续执行：`gitea_create_branch`（feature/demo-backend）→ `gitea_commit_files` → `gitea_create_mr`（feature/demo-backend → develop）。

## 6. 验收清单（跑通的判据）

- [ ] Gitea 仓库出现 **feature/demo-backend** 分支；
- [ ] 分支上有数字员工的 **commit**（文件内容在仓库可见）；
- [ ] 出现 **Pull Request**（feature/demo-backend → develop），描述含汇报说明；
- [ ] 控制台「任务详情」节点验收走完 申报 → 放行；任务最终 **已完成**；
- [ ] 「审计台账」有完整工具调用链（含 gitea_* 调用）与审计链校验通过。

## 7. 常见问题与兜底

| 现象 | 原因 / 处理 |
|---|---|
| gitea 工具 401 | PAT 错误 / scope 没勾 repository write；重新生成并验证 `curl .../api/v1/user` |
| gitea 工具 404 | repo.url 与实际仓库不一致（推导规则 `host/owner/repo.git` → `owner/repo`）；或 MR 目标分支 develop 未建 |
| change_files 404 | Gitea < 1.20，属预期：自动回退逐文件提交（每文件一个 commit），MR 照常创建 |
| 模型端点 401/超时 | routes 的 baseUrl 需含 `/v1` 类版本路径（OpenAI 兼容约定）；key 解密失败检查 DDW_CRED_KEY |
| 想纯流程演示不依赖云端 | 启动加 `--exec-mode fork --agent-module demo/faux-agent.mjs`（即 demo.mjs --mock 的手动等价，预设回复，不访问模型） |

## 附录 A：换回 GitLab 自托管

`forge.provider: gitlab`（缺省即 gitlab），`baseUrl` 填服务根地址（前缀 `/api/v4` 自动拼接），PAT scope 用 `api`。工具名为 `gitlab_*`，其余流程完全一致。

## 附录 B：本次新增能力说明（2026-09-05）

- runtime yaml 新增 `forge` 段（provider: gitea | gitlab），配置后员工工具集自动注入对应托管工具；
- `defaultRepo` 由任务包 `repo.url` 自动推导，员工调用工具不必传 repo 参数；
- token 支持 `enc:v1:` 密文（与模型 apiKey 同一套主密钥机制）；
- inproc 与 fork 两种执行模式均透传 forge 配置（fork 经 worker IPC）。
