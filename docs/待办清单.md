## 🔴 高优先

### 1. doctor 明文巡检覆盖不全

- **现状**：`doctor.ts` 的「敏感凭据密文化」巡检项按已知敏感字段路径做**结构化 yaml 解析**排查明文，但未覆盖 `yanxun:` 段（内部通知渠道端点配置）与员工 yaml `profiles` 里的 `model.apiKey`。
- **为什么是问题**：巡检是明文落盘的最后一道兜底防线，覆盖面有洞 = 新增配置段时静默漏检，防线形同虚设。
- **建议方案**：敏感字段路径清单集中维护（一处常量），doctor 遍历清单而非散落硬编码；补 `yanxun` 段与 `profiles[].model.apiKey` 两条路径；新增敏感字段时强制同步清单（可加测试约束）。

## 🟡 中优先

### 2. 班组编排依赖失败不向下传递

- **现状**：`scheduler.ts` 的 `readinessOf` 只看**直接依赖**的状态——传递依赖（依赖的依赖）failed 时，孙节点仍显示 `waiting` 而非 `blocked`。
- **为什么是问题**：看板语义失真——运维/管理者看到的孙节点像「还在排队」，实际注定不会执行；人工排查成本高，也可能误判调度器卡死。
- **建议方案**：readiness 计算改为传递闭包（沿 dependsOn 递归下探，任一祖先 failed/blocked 即 blocked）；顺带在任务详情页展示被哪个上游任务阻断。

### 3. 任务无优先级字段

- **现状**：同批次任务纯 FIFO 分派（`ddw_tasks` 按 `ORDER BY created_at, id` 取队首），无优先级概念。
- **为什么是问题**：急活（线上缺陷修复、演示保障）无法插队，只能等前排任务跑完；实际研发排产中优先级是刚需。
- **建议方案**：任务包 yaml 增 `priority` 字段（贯通全链路：parseRuntimeConfig → 任务包固化 → 存储），分派排序改为 `ORDER BY priority DESC, created_at ASC`；sqlite/mysql 双驱动同步迁移加列；管理台任务列表展示优先级徽标。

### 4. ddw_events 只增不减，无冷数据归档方案

- **现状**：审计红线明确**事件表一条不删**（hash 链合规要求），`retention.ts` 的磁盘治理明确把 events 排除在治理外；长跑环境下表体积线性增长（含 payload，是全库增长最快的一张表）。
- **为什么是问题**：审计红线不能碰，但「只增不减」没有归档/分区方案意味着容量只靠扩盘硬扛；查询也会随体积变慢。
- **建议方案**：按时间冷热分层——超期（如 6 个月）事件迁入归档表/归档库（保留完整链、可校验），主表只留热数据；或利用 MySQL 分区表按月分区。关键约束：**任何迁移方案必须保持 hash 链全链可校验**（`POST /api/audit/verify` 对归档数据同样成立），且纳入备份恢复演练手册的演练范围。

### 5. 前端 SSE 覆盖不全

- **现状**：`apps/console/src/live.ts` 的 agent-event 单例订阅已建好（EmployeeLive/TaskCenter 已接 SSE + 轮询兜底），但 Dashboard（首页面板）、CheckReview（人工放行）、TaskDetail（任务详情）、Employees（数字员工名册）四页仍是 5s 轮询。
- **为什么是问题**：同一事件流两套机制并存，未接入的页面实时性差且空转轮询浪费；后续每页维护两套刷新逻辑心智负担大。
- **建议方案**：四页逐一接入 live.ts 单例（沿用「SSE 在场时空转跳过、断线自动恢复」的既有降级模式）；完成后评估关闭纯轮询兜底的开关。

## 🟢 低优先

### 6. doctor 体检仅 CLI 入口

- **现状**：体检只有 `cli.ts doctor` 一个入口，无 HTTP API、无管理台页面。
- **为什么是问题**：非运维人员（如试用行方）想看系统健康状态只能上机器敲命令；前端也无从展示健康度。
- **建议方案**：doctor 核心检查逻辑抽纯函数层，暴露 `GET /api/health/detail`（鉴权内），管理台首页加健康卡片；注意巡检项里「端口未占用」等仅适合启动前跑的项要做适用性标注。

### 7. logger 无轮转

- **现状**：轻量 logger 只做分级与 `[ddw:模块]` 前缀，不做文件轮转，依赖 pm2/systemd 的日志管理。
- **为什么是问题**：内网单机部署若不经进程管理器裸跑，日志无界增长。**已知取舍**——部署手册本就要求 systemd/pm2 常驻（自带轮转），可接受；裸跑场景属非推荐用法。
- **建议方案**：暂不处理；若未来出现裸跑需求，再评估按天/按大小轮转或接入 pino-roll 类方案。

### 8. CORS / 安全响应头未显式设置

- **现状**：console-api 未显式配置 CSP、X-Frame-Options、CORS 等安全响应头。
- **为什么是问题**：内网同源部署下实际攻击面很小（低危），但安全评审可能追问；若未来控制台与 API 跨域部署，缺 CORS 会直接不可用。
- **建议方案**：http server 统一中间件补 `X-Frame-Options: DENY`、基础 CSP、显式同源 CORS（拒绝跨域）；配置化放行反代场景。

### 9. 模型 thinking/reasoning 内容不进员工直播

- **现状**：`event-map.ts` 只映射 text 块进 thinking 事件；模型的 thinking/reasoning 专用内容块不映射，前端直播看不到。
- **为什么是问题**：监督场景少一路「员工在想什么」的可见性；不过 token 开销经 usage 记账部分可见。**已知取舍**——映射会显著放大事件体积与前端渲染压力。
- **建议方案**：评估折中——直播流只推 thinking 摘要（截断/采样），完整内容落 session 文件按需查看；先做任务详情页「查看原始会话」入口。

### 10. 优雅停机不等 in-flight 执行完成

- **现状**：SIGTERM 优雅停机只停接新连接/断 SSE/停定时器，在途任务不等待完成，由下次启动孤儿扫描接管（标 failed 可续跑）。
- **为什么是问题**：发布重启会打断正在执行的任务。**设计取向**——执行动辄几十分钟，等待 in-flight 等于发布窗口不可控；孤儿扫描 + 断点续跑 + 强制重置已是完整的双保险闭环。
- **建议方案**：保持现状；可选增强——重启前经 API 广播「即将维护」通知，或提供 `--drain` 模式（等当前批次跑完再退，仅维护窗口手工使用）。

### 11. inproc 模式无执行内超时

- **现状**：任务级看门狗（`taskTimeoutMs`）对 inproc/fork 双模式生效（DB 侧收割），但 inproc 单次执行内部无独立超时（fork 有子进程 kill 兜底）。
- **为什么是问题**：inproc 下模型 hang 由模型网关 120s 超时 + 看门狗双保险兜底，实际风险已被覆盖。**已知取舍**。
- **建议方案**：保持现状；若未来 inproc 用于长跑生产，评估 per-turn 超时注入（与模型网关 AbortSignal 同一机制收口）。
